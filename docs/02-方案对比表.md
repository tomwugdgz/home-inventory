## 一、核心需求与痛点复核（三要素）

按 requirement-analysis.md 第 1.1 节五要素法复核，先确认三要素再谈方案（避免 D1「把方案当需求」翻车）。

### 1.1 做什么（业务目标）

**一句话表述**：做一个「随手记、一碰查」的家庭物品收纳管理工具——用手机拍照 AI 识别或 NFC 贴标签即可登记物品，记录它是什么、放在哪个收纳位置，之后随时能快速找到。

这不是电商、不是社交，本质是**个人/家庭级的轻量资产台账 + 空间索引工具**。核心价值闭环是：

> 发现/购入物品 → 3 秒内完成登记（拍照 AI 或碰 NFC）→ 系统归入某个收纳位置 → 日后「东西放哪了」时一查即得。

### 1.2 面向谁（目标用户）

| 角色 | 描述 | 权重 |
|------|------|------|
| 主用户（发起人 Tom） | 家庭物品管理者，负责录入、整理、归类 | 第一优先级 |
| 次级用户（家庭成员） | 配偶/家人，偶尔查询「XX 在哪」，不应被要求安装 App | 第二优先级 |

**关键区分**：发起人（Tom，愿意折腾登记）与使用者（家人，只想查一下）诉求不同。这直接决定了小程序不是可选项——家人不会为一个「查一下」的需求去装 App 并注册账号。这一点与 platform-selection.md 案例 1（社区团购，顾客不会为接龙装 App）逻辑一致。

### 1.3 核心目标（价值与成功标准）

- **主观目标**： Tom 明确说「越简单越好」——这是产品第一设计约束，高于功能丰富度。
- **可测成功标准（首个数字）**：🟡 待确认。建议采用「登记一件物品平均耗时 ≤ 10 秒」+「上线 1 个月内登记物品 ≥ 100 件」作为北极星指标，需 Tom 认可。

### 1.4 核心场景与用户故事（KANO 简化分类）

| 编号 | 类型 | 用户故事 | 验收标准 | 优先级 | 进 MVP |
|------|------|----------|----------|--------|--------|

### 1.5 待确认问题清单（影响方案与排期）

1. 🟡 **预算上限**：开发预算 + 年度运行费（服务器/证书/API）各是多少？——直接决定 A 方案自托管是否成立，以及是否够得上双端工期。
2. 🟡 **期望上线时间**：是否要求 3 个月内可用？——决定能否承受 A 的二开磨合 + 双端工期。
3. 🟡 **技术维护能力**：Tom 是否有后端运维能力/愿意维护一台服务器？——这是 A 方案的**前置条件**，若无则 A 的运维成本评分需下调至 1 分。
4. 🟡 **主体资质**：个人开发者还是公司/个体户？是否已有域名并完成备案？——微信小程序认证、App 上架、后端域名 HTTPS 均依赖此项（见 platform-selection.md 合规速查表）。
5. 🟡 **NFC 预算**：是否愿意采购 NFC 贴纸（约 0.3~1 元/张）并接受「NFC + 二维码」双轨？——决定 NFC 是否为唯一入口。

## 二、平台形态结论校验（为什么 App + 小程序双端合理）

### 2.1 四步设备习惯判断法（引用 platform-selection.md 第 2.1 节）

| 步骤 | 判断 | 结论 |
|------|------|------|
| ① 画用户状态 | Tom 在储物间/阳台/客厅，手持手机，处于「刚发现物品/找不到东西」的碎片状态 | 移动端优先，必须「随手记」，桌面/Web 排除 |
| ② 判使用频次 | 录入碎片高频（购物/整理时），查询低频刚需（找不到时）；单看查询属低频，装 App 会被卸载 | 小程序承接「家人临时查」，App 承接「管理者高频录」 |
| ③ 判人群设备构成 | iPhone / 安卓混用（用户明确） | **必须跨端双端覆盖，不可只做 iOS**；排除原生双端（成本过高） |
| ④ 判关键动作 | NFC 读写 + 摄像头 AI 识别 = 系统级能力 | 主战场在 App；小程序做查询与二维码兜底 |

### 2.2 决策树路径结论

按 platform-selection.md 第五章决策树逐层走：

```
合法合规？ → 是（工具类，无社交/支付/医疗等强资质类目）
用户主要设备？ → 移动端 + 需系统能力（NFC/摄像头）
  → 「移动高频 + 需推送/系统能力」分支
  → 同时需要小程序 → 「跨端 + 小程序组合」分支
  → 预算与团队能力？ → 🟡 待确认（假设个人/小团队、预算有限）
  → 常规 → Flutter / RN 跨端
是否需要 B 端管理后台？ → 否（家庭工具，无运营侧）
输出 → 跨端 App（iOS + Android）+ 微信小程序 + 轻量云端/自托管后端
```

**结论**：团长已定的「App + 小程序双端」形态成立，本报告不推翻，仅校验其合理性并指出 NFC 现实约束。

### 2.3 NFC 混用机型的现实约束（关键风险，必须前置说明）

这是本次选型**最容易被低估的技术约束**，直接影响 A/B/C 的 NFC 得分：

| 环境 | NFC 能力 | 约束 |
|------|----------|------|
| iPhone（App） | Core NFC，iPhone 7+ 支持 | 读 NDEF 需在 entitlements 声明；**写入 NDEF 标签需额外权限，审核有不确定性** |
| 安卓（App） | NFC 权限开放 | 机型碎片化：部分低端机无 NFC；NFC 感应区位置不一，需 UI 引导 |
| 微信小程序 | `wx.getNFCAdapter` | **iOS 上能力明显受限、依赖基础库版本与机型**；写卡能力弱 |

**由此得出三条硬结论**：
1. NFC 不能作为唯一标识入口，必须「NFC + 二维码/条码」双轨——碰一碰是体验，扫一扫是兜底。
2. NFC 主战场在 App 端；小程序端以扫码查询为主，不承诺完整 NFC 写入。
3. Homebox 原生就有二维码/条码体系——这在 NFC 受限的现实下反而是**资产而非包袱**，是 A 方案加分的重要依据。

### 2.4 触达能力与合规校验

- 触达（platform-selection.md 第十章）：App 厂商推送强召回；小程序订阅消息中、需用户逐次授权。对「耗材/保质期提醒」（REQ-008）而言 App 明显更强，这也是该需求虽延后但应放 App 的原因。
- 合规：工具类无强资质类目，但**微信小程序需微信认证 + 服务器域名 HTTPS 备案（认证 1~3 天，审核 1~7 天）**；**App Store 需 Apple Developer 账号（99 美元/年）**；安卓商店多要求软件著作权。以上均需 🟡 Tom 确认主体资质。

## 五、唯一推荐与备选（明确结论）

### 🏆 主推荐：方案 A —— 基于 Homebox + companion 二次开发

**理由（三条，对应最高权重项）**：

1. **数据模型贴合度 5 分是决定性优势**：家庭收纳的骨架是「位置树 + 标签 + 照片 + 搜索」，Homebox 已全部实现并经过 7918★ 项目的实战检验。B/C 都要从零设计这套模型，而它恰恰是 MVP 里 REQ-001/002/003/007 四项基本/期望型需求的基础。在这一项上省下的设计与返工成本，足以抵消 A 在双端和 NFC 上的劣势。
2. **AI 识别有现成轮子**：companion（421★）直接提供拍照 AI 识别，对应 REQ-004。B/C 需自接第三方视觉 API，物品细粒度准确率不稳定，而「识别准、少打字」正是「越简单越好」的核心体验。
3. **隐私掌控 5 分契合家庭数据属性**：家庭物品照片 + 房间布局属敏感信息，自托管数据完全自有，无第三方 BaaS 让渡问题。

**推荐落地策略（扬长避短）**：
- 以 Homebox 为后端底座，**前端双端 App 用跨端框架（RN 或 Flutter）新写**，不要试图把 Vue Web 套壳成 App——混用机型要的是原生 NFC 与相机体验。
- **NFC 走「UID 绑定 + 二维码兜底」双轨**：后端为物品加 NFC UID 字段与绑定 API，App 端做碰一碰读取；二维码沿用 Homebox 原生能力，覆盖小程序与无 NFC 机型。
- 小程序独立轻量开发，只做「扫码查询 + 位置查看 + 手动登记」，不承担 NFC 写入。
- 配送一键部署脚本 + 自动备份，把 A 的运维短板压到最低。

**主推荐成立的前提（🟡 必须确认）**：Tom 愿意维护一台服务器（或团队有运维能力），且预算能覆盖双端 App + 小程序的开发量。若此前提不成立，A 的运维成本评分应从 2 下调至 1，总分降至 3.39——仍略高于 B/C，但优势明显收窄。

### 🥈 备选一：方案 B（Expo 自研）—— 切换条件

若出现以下任一情况，切换到 B：
- Tom **明确拒绝自托管运维**（不愿管服务器/备份/证书），且更看重 NFC 体验的原生可控；
- 团队是 Web/React 背景，Expo 上手最快，且愿意接受从零数据模型的返工风险；
- 愿意把小程序改用 Taro/uni-app 一套多端实现（此时小程序可得性升至 4，B 总分约 3.31）。

### 🥉 备选二：方案 C（Flutter + 云 BaaS）—— 切换条件

仅当 **预算充裕 + 追求最佳双端体验 + 完全不想运维 + 接受数据在第三方云** 时选择。对当前「越简单越好」的轻量家庭工具而言，C 的完全从零属于过度投入，无差异化收益，**本阶段不推荐**。

## 八、结论摘要

- **需求三要素已复核**：做什么=家庭物品随手登记与查找工具；面向谁=Tom（录入）+ 家人（查询）；核心目标=登记 ≤10 秒、一碰即查。MVP 锁定 REQ-001~007 共 7 项。

- **唯一推荐**：**方案 A（Homebox + companion 二开）**，加权 3.49，凭数据模型与 AI 现成资产胜出；备选 B（拒绝自托管时）、C（预算充裕且追求免运维时，本阶段不推荐）。
